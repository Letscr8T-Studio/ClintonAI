# Phase 3: Chrome extension (Clinton AI inside Gmail)

**Status:** In progress (opened 2026-11-13 by founder decision, ahead of the Phase 1 gate; see
[decisions](../decisions.md)). Phase 1 continues in parallel: Google verification, beta, Yahoo
deliverability. **Gate to the next phase:** Chrome Web Store approval.

## Goal

People write in Gmail's own compose window and still get Clinton AI: the AI check with inline
highlights, and a **Send with Clinton AI** button that offers Smart Delay, Send later and Safe Send.
Same account, same settings and same Outbox as tryclinton.com. Desktop only (Chrome, Edge, Brave,
Opera, Arc). Phones keep using the web app.

## Out of scope

Reading the inbox or any received email; replacing or catching Gmail's own Send button; Firefox and
Safari; Gmail mobile app (a Google Workspace add-on is a separate, later decision); Outlook web;
outreach features; payments.

## User stories (acceptance criteria)

1. **Install and connect:** I install from the Chrome Web Store and click the Clinton AI icon. If I'm signed in on tryclinton.com, it already knows me; if not, one button takes me to sign in. Under 1 minute.
2. **Check while I write:** in Gmail's compose window a small Clinton AI bar shows "Checking…", then "All good" or "2 things to check". Highlights appear on the words; each has Fix it / Ignore. Nothing is checked until I've stopped typing for ~1.5 s, and nothing is ever blocked.
3. **Gmail's Send still works:** if I use Gmail's own Send, Clinton AI stays out of the way. The email is not held, tracked or recorded by us.
4. **Send with Clinton AI:** the Clinton AI pill opens a panel: what the check found, then the send options (when: Smart Delay or a Send later pick; Safe Send; "Likely opened") and **Send with Clinton AI**. It goes to the Outbox, Gmail's draft is discarded (so it can't also go with Gmail's Send), and a note at the bottom of Gmail says when it leaves, with Undo and Outbox. Undo takes it back and reopens it, filled in, in a new Gmail compose window.
5. **Outbox anywhere:** the toolbar popup lists what's waiting (countdown, Cancel, Send now) and what can still be withdrawn. Everything links to tryclinton.com for the full view.
6. **Disconnect:** signing out of tryclinton.com signs the extension out at the same moment; removing the extension removes everything it had (it stores nothing).
7. **Honest about limits:** formatting and pictures: sent as plain text, said before sending (link addresses are kept: "the plan (https://…)"). Gmail attachments, replies and forwards, and a Gmail tab that isn't the connected account: no Send with Clinton AI button, and the panel says why; Gmail's Send is the way for those.

## How it works

```
mail.google.com tab                     extension service worker            tryclinton.com
┌──────────────────────────┐   message   ┌───────────────────────┐  HTTPS   ┌──────────────────┐
│ content script            │ ─────────▶ │ holds the device token │ ───────▶ │ /api/check       │
│  · finds compose windows  │ ◀───────── │ calls the API          │ ◀─────── │ /api/emails …    │
│  · reads To/Cc/Bcc/subject│            └───────────────────────┘ Bearer   │ (same routes as  │
│    /body of THAT window   │                                                │  the web app)    │
│  · draws bar + highlights │                                                └──────────────────┘
└──────────────────────────┘
```

- **Manifest V3.** No API permissions so far; add one only when a milestone needs it (`storage` likely for per-device preferences). Host permission: `https://tryclinton.com/*`; a content script on `https://mail.google.com/*` (milestone 3). Never `tabs`, `history`, `cookies`, `<all_urls>`, `scripting` or remote code. The manifest is generated by `scripts/build-extension.mjs`.
- **Content script** (`extension/src/content/`; UI in a closed shadow root so Gmail's CSS and ours never mix). It reads only compose windows the user is writing in, never the message list or opened emails, and leaves quoted earlier messages and the signature out of the body. Gmail's page is undocumented: every selector lives in `extension/src/gmail/selectors.ts`, tested against fixtures in `extension/src/gmail/fixtures/`, so a Gmail change is a one-file fix. A compose window is the smallest element around an editor that also holds a Send button.
- **Dev builds only** (`npm run ext:dev`): a Debug panel in Gmail shows what was read, and **Copy structure** copies an anonymised outline of the window (no text, values, names or addresses) to refresh the fixtures from real Gmail. The store build contains none of it (`__DEV__`).
- **Service worker** makes every API call; pages and content scripts ask it by message (`extension/src/messages.ts`) and accept messages only from this extension.
- **The extension sends nothing by itself.** It creates an email with the existing `POST /api/emails` and our dispatcher sends it from the user's own Gmail, exactly like the web app (trust rule 5). Gmail's Sent folder shows it as usual.

## Connecting the extension (auth)

**The extension uses the tryclinton.com session itself** (decided 2026-11-13, see decisions). With
host permission for the site, Chrome attaches the site's cookies to the service worker's requests
and treats them as same-site, so the existing routes work unchanged:

- No token, code exchange, new table or second way in to secure; the extension stores nothing.
- Signing out on the site signs the extension out; Supabase refreshes the session as usual.
- Repositories keep running as the user under row-level security.
- No CORS headers are added, so ordinary websites still can't read the answers.
- Proven live on 2026-11-13: the built extension in Chromium against the local app, signed out → no Gmail → ready.

Fallback if a browser ever stops attaching the cookies: device tokens (hashed, revocable) handed over
from a signed-in page via `externally_connectable`. Not built.

## Data model

None so far. The extension reads and writes through the same tables and routes as the web app.

## Routes (new or changed)

| Route                               | Purpose                                                                       |
| ----------------------------------- | ----------------------------------------------------------------------------- |
| `GET /api/me`                       | Built. Who is signed in, Gmail account and status, default delay (`meSchema`) |
| `/api/check`, `/api/emails`, outbox | Unchanged; called by the service worker with the site's session               |
| `GET /api/outbox`                   | Built. What the popup can still act on (`popupOutboxSchema`)                  |

## Repo layout

`extension/src/` beside `src/`, in the same package (one install, one `npm run check`): TypeScript,
React for the popup, `@/` imports from `src/` so validation, copy, UI primitives and later the check
rules are one copy. `npm run ext:build` (store build, tryclinton.com) and `npm run ext:dev` (local app)
write `extension/dist` with Vite; the popup's CSS is Tailwind limited to its own files and the
design tokens. Copy lives in `src/content/extension.ts`. Same conventions: ~150 lines per file,
tokens for colours, axe on the popup.

[x] Popup Outbox (2026-11-13): `GET /api/outbox` (only what can still be acted on, soonest first: waiting emails and withdrawable Safe Sends; subjects and recipients, never text; `popupOutboxSchema`), live countdowns, Send now, Cancel and Withdraw for everyone (both confirm first) through the Outbox page's own routes, reloaded after each action and when a countdown ends. - **Gmail attachments.** Not readable from the page. v1 offers "Open in Clinton AI"; later, re-attach in our own picker?
- ~~Check data~~ Decided 2026-11-13: checking while typing, with the limits in milestone 4 (pause, changed content only, signed in, recipient and text present). Same route, same 30-a-minute limit, text still never stored. The privacy policy must say the extension does this (milestone 7).
